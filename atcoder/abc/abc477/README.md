## C. Range Search Query

文字列$S$と$T$が与えられます。$Q$個のクエリ、一個ずつ$L,R$で、$S$の$L$番目の文字から$R$番目の文字までの部分文字列に、$T$が含まれているか、判定せよ。

$|S|=N$をし、$|T|=M$をし、まずは$M\leq 10$だと書いてあったので、全探検でも十分だと思いましたが、TLEです。なぜなら、クエリずつ、$S$全体スキャンしたから$O(NQ)$になって$10^{10}$以上の操作になってきました。

正直、今回は考えるの忘れて、バーチャルコンテストの直後解説すぐ読んだのです。また総和で解けると書かれて、何度も繰り返して提出していたあげく、ACはできました。Uiuaの[`find`](https://www.uiua.org/docs/find)と少し同じで、初期化として$S$の中に、部分文字列$T$が現れたら、$1$とする。そうでなければ、$0$とする。それで、累積和配列を計算する。

$$
A = (0,1,0,0,1,0,0), P = (0,1,1,1,2,2,2)
$$

例えば、例の累積和配列にては、$L=2,R=4,M=2$だとしたら、$P_{L-1}=0,P_{R-M+1}=1$で、$1>0$なので、`Yes`となります。なんか、クエリのレンジには、$1$の$A_i$が存在しているかどうか、判定するということです。でも、それをしたら、TLEになってしまうので、累積和配列が必要です。

でも、それだけではなく、解き方がわかりながら、変なケースにはまだ例外があるので、ACになれなかった。特には、例の部分文字列が頭にある場合です。

```plaintext
3
abbccddeeff
a
2 10
1 1
1 3

No
Yes
Yes
```

以上の例には、WAになっています。一時間くらい、なんでACできなかったのか何が間違ったのか、テストケースを作ってみました。提出の詳細をみると、`corner`というケースがWAであって、頭にある部分文字列または尾にある場合も作ると、その間違いがわかるようになりました。

$L=1,R=1$では、$P_{L-1}$は存在しないため、$P_1$で初期化していたことこそが、間違いでした。これで、クエリを処理しはじめるまえに、累積和配列の頭に$0$を追加してのちはACできました。

## E. Wheel Distance

$N+1$頂点があります。$A_1,A_2,...,A_N$が与えられて、それぞれ$A_i$が頂点$i$と頂点$(i \mod N)+1$の辺である。それで、$B_1,B_2,...,B_N$が与えられ、それぞれ$B_i$が頂点$i$と頂点$N+1$の辺である。$Q$個のクエリで、頂点$A$と頂点$B$の最短距離を求めよ。

これ読めば、グラフの問題にみえると思いました。大学にいたときは、ある開始頂点からゴール頂点まで最短パスを求めたいなら、普通にA\*というアルゴリズム使うのですが、一つのクエリであったら十分に速いと思いますが、$Q\leq 10^5$のクエリであれば、TLEの可能性も非常に高そうです。それで、書いてみると、問題の名前通り、グラフだけではなく、周りの輪と中心のハブみたいなグラフです。

では、この問題には、どうやって、二つの頂点の最短距離を先に計算して、クエリを処理するときはただルックアップすれば済むという問題です。少し考えてみれば、二つの頂点$i$と$j$の最短パスは以下の三つのケースにわかれています、

1. 中心頂点を通る場合には、$D_1 = D(i,N+1) + D(j,N+1)$.
2. 中心頂点を通らない場合には、以下のようにまた二つのケースにわかれます。
    1. 周りを時計回りに行く場合、$D_2$と呼びます。
    2. 周りを反時計周りに行く場合、$D_3$と呼びます。

$A$から$B$までの最短距離は$D=\min(D_1,D_2,D_3)$ということになっています。これまではおそらくそなたも流れを把握できるようになりましたね。場合ずつに解けるのがいいです。

ほぼ半分の経路は中心頂点を通るので、まずは中心から他の全ての頂点に最短距離を求めます。Dijkstraこそがこの理由でデザインされたアルゴリズムです。それで、また一つのことが、周りの輪にはループしているので、$S$は周りの外周で、$D_2=S-D_3$です。
