## C. Range Search Query

文字列$S$と$T$が与えられます。$Q$個のクエリ、一個ずつ$L,R$で、$S$の$L$番目の文字から$R$番目の文字までの部分文字列に、$T$が含まれているか、判定せよ。

$|S|=N$をし、$|T|=M$をし、まずは$M\leq 10$だと書いてあったので、全探検でも十分だと思いましたが、TLEです。なぜなら、クエリずつ、$S$全体スキャンしたから$O(NQ)$になって$10^{10}$以上の操作になってきました。

正直、今回は考えるの忘れて、バーチャルコンテストの直後解説すぐ読んだのです。また総和で解けると書かれて、何度も繰り返して提出していたあげく、ACはできました。Uiuaの[`find`](https://www.uiua.org/docs/find)と少し同じで、初期化として$S$の中に、部分文字列$T$が現れたら、$1$とする。そうでなければ、$0$とする。それで、累積和配列を計算する。

$$
A = (0,1,0,0,1,0,0)
P = (0,1,1,1,2,2,2)
$$

例えば、例の累積和配列にては、$L=2,R=4,M=2$だとしたら、$P_{L-1}=0,P_{R-M+1}=1$で、$1>0$なので、`Yes`となります。なんか、クエリのレンジには、$1$の$A_i$が存在しているかどうか、判定するということです。でも、それをしたら、TLEになってしまうので、累積和配列が必要です。

でも、それだけではなく、解き方がわかりながら、変なケースにはまだ例外があるので、ACになれなかった。特には、例の部分文字列が頭にある場合です。

```plaintext
3
abbccddeeff
a
2 10
1 1
1 3

No
Yes
Yes
```

以上の例には、WAになっています。一時間くらい、なんでACできなかったのか何が間違ったのか、テストケースを作ってみました。提出の詳細をみると、`corner`というケースがWAであって、頭にある部分文字列または尾にある場合も作ると、その間違いがわかるようになりました。

$L=1,R=1$では、$P_{L-1}$は存在しないため、$P_1$で初期化していたことこそが、間違いでした。これで、クエリを処理しはじめるまえに、累積和配列の頭に$0$を追加してのちはACできました。
